# PatchPitch состояние проекта практические сценарии и роадмап

Срез на 21 октября 2026 года, main `6f840045db76fb759bf7c3ab09f20cb0ff449356`.

Последующая локальная реализация сохранения и Git importer описана в [Сессии и DevLog из Git](sessions-git-devlogs.md). Ниже сохранён исходный срез аудита до этих изменений.

PatchPitch уже можно использовать как локальный редактор для подготовки DevLog, постов о продукте и объяснений игровых механик. Самый полезный следующий шаг — сократить путь от последних коммитов до проверенных фактов и готового DevLog. Сохранение сессии и надёжная привязка текста к источникам нужны этому сценарию раньше новых моделей и интеграций.

Ниже — оценка реализации, issues, подробные сценарии до ручной публикации и порядок развития. Публикация в рамках аудита не выполнялась.

## Текущее состояние

### Что уже работает

| Возможность | Реальное поведение |
| --- | --- |
| Ввод материала | Продукт, описание, аудитория, release label, 1–15 заметок общей длиной до 6000 символов, голосовой образец и CTA |
| Отбор фактов | Include/Exclude; planned/internal/blocked/unknown и Unreleased исключаются по умолчанию, затем пользователь подтверждает выбор |
| Повторяемые входы | Два встроенных fact pack и импорт JSON; загрузка сама не вызывает модель |
| Devlog | Заголовок, вводная часть, основные изменения, дополнительные темы и обязательная заметка, когда она распознана |
| Community post | Связный текст до 1600 Unicode characters |
| Short post | До 280 Unicode characters вместе с CTA и tags; это общий лимит, не проверка конкретной соцсети |
| X Single и X Thread | Одна карточка или 3–7 карточек; редактирование, перестановка, повторная генерация одной карточки, отдельные media notes |
| Проверка результата | Исходные заметки, ссылки Cxx, предупреждения о некоторых числах, ссылках, пропусках и ограничениях |
| История попыток | Generation records с исходными API responses, ошибками и моделями; ручные правки сохраняются отдельно от оригинала |
| Экспорт | Markdown и JSON record; Copy одной X карточки даёт только её текст |
| Локальная модель | Ollama на 127.0.0.1:11434; текущая конфигурация gemma4:12b; один запрос на явное действие |

История, вход и варианты остаются только в памяти текущей вкладки. JSON record полезен для разбора попытки, но загрузки сессии из него пока нет. Ссылки Cxx показывают, какой источник указан, а не доказывают смысл каждого предложения.

### Как устроен код

`patchpitch/app.py` предоставляет локальный HTTP API и static frontend, ограничивает Host/Origin и размер JSON, запрещает параллельную генерацию внутри процесса. `models.py` описывает строгие входные и выходные структуры. `generator.py` и `social.py` строят запросы Ollama и возвращают исходный ответ вместе с результатом проверки.

`validation.py` содержит выбор заметок, проверки структуры, несколько лексических правил и Markdown export. `fact_packs.py` готовит повторяемые факты и provenance. На клиенте `app.js` ведёт форму и обычные форматы, `social-editor.js` — карточки X, `generation-records.js` — историю попыток. Базы данных и аккаунтов нет.

Отдельный слой `scripts/` предназначен для настройки, проверки модели, сравнения генераций и подготовки записанного демо/видео. Это инструменты разработчика; они не являются пользовательским импортом Git или публикацией. Часть их метаданных осталась привязана к исторической конкурсной записи.

Архитектура подходит для ближайшего local Git → fact review → Devlog сценария. Для него не нужны React, облачная база, агент с доступом к shell или общий фреймворк интеграций. Главные слабые места находятся в согласованности состояния редактора, provenance и подготовке входных фактов.

### Что пока делается вручную

- Извлечение смысла изменений из Git. Commit messages нельзя считать готовыми проверенными фактами.
- Проверка того, что код действительно доступен пользователям. Merge, tag, deployment и публичный анонс — разные события.
- Редактура смысла: условия, последовательность выполнения, ложная новизна, голос автора и польза для читателя.
- Сохранение файлов перед закрытием вкладки.
- Перенос текста, изображений, заголовка и tags в редактор площадки, preview и публикация.
- Русский текст: все три промпта сейчас явно требуют English. Voice sample не является переключателем языка. EN/RU находится в [#6](https://github.com/drevendev/PatchPitch/issues/6).

### Результаты проверки

Полный существующий unit/API/browser/privacy suite: **206 passed, 15 dependency warnings, 36.77 секунды**. Ответы модели в этих тестах MOCK. Первоначальный запуск внутри песочницы блокировал loopback sockets; итоговый прогон выполнен с разрешением локальных сокетов и Chromium.

Дополнительно выполнены три запроса к настоящей установленной `gemma4:12b`, по одному на сценарий, с текущими импортированными исходниками и выключенной Sentry:

| Вход и формат | Результат проверки приложения | Время запроса |
| --- | --- | --- |
| Последние изменения generation records в PatchPitch → Devlog | Принят, warnings отсутствуют | 35.360 с |
| Исторические факты Idle Fantasy Shop 0.12 → Community | Принят, warnings отсутствуют | 11.120 с |
| Публичный workflow PatchPitch → X Thread из 5 постов | Принят, warnings отсутствуют | 15.577 с |

Это одиночные наблюдения на этой машине. Они подтверждают получение текста через текущий backend, но не являются замером скорости продукта или одобрением владельца. Прогон реальной модели выполнен напрямую через Python backend; поведение интерфейса и clipboard/export отдельно проверяется браузерными MOCK тестами.

Уже работающий сервер на 8000 отвечал ready, но его runtime fingerprint отличался от текущего checkout. Поэтому новые live результаты получены из текущего кода отдельно; чужой рабочий процесс не перезапускался. После обновления проекта следует перезапустить своё окно приложения.

Пример необходимости редактуры: игровой Community output начинается с «can now manage multiple jobs at once». Источник описывает историческую функцию 0.12 и последовательную очередь. Позже текст правильно поясняет порядок, но открытие всё равно нужно исправить. Нулевые warnings этого не заметили. Конкретный пример добавлен в [#48](https://github.com/drevendev/PatchPitch/issues/48) и [#53](https://github.com/drevendev/PatchPitch/issues/53).

Локальные результаты аудита находятся в `artifacts/audit-2026-10-21/`, исключённом из Git. Там сохранены исходные входы/ответы, а также воспроизведения дефектов. Их нельзя считать опубликованными материалами.

## Подготовка к работе

### Запуск на этой машине

Открой PowerShell в корне PatchPitch. Если приложение уже запущено из старого checkout, останови его своим Ctrl+C и запусти снова. Перед этим скачай нужные черновики из вкладки: её refresh удаляет текущее состояние.

```powershell
$env:PATCHPITCH_MODEL = 'gemma4:12b'
$env:PATCHPITCH_SENTRY_DSN = ''
.\scripts\start_local.ps1
```

Открой `http://127.0.0.1:8000`. Окно PowerShell должно оставаться открытым. Статус модели должен показывать local и установленную модель. На этой машине модель доступна; новый download для этих сценариев не требуется.

Для чистого checkout установка Python environment, dependencies и Ollama описана в [README](../README.md). Launcher сам не скачивает модель. Если виден model_missing, проверь модель у того сервера Ollama, который обслуживает 127.0.0.1:11434. У portable runtime и системной установки могут быть разные каталоги моделей. Модель gemma4:12b на проверенной машине занимает около 8 GB на диске; это не оценка требуемой оперативной памяти.

### Общий цикл подготовки текста

1. Загрузи pack либо заполни Product name, What does it do?, Who is this for?, Release и What changed?. Одна самостоятельная заметка — одна строка.
2. Раскрой Choose your facts. Прочитай оригиналы и ограничения; оставь только факты нужного сценария. Непубличные и внутренние сведения не добавляй в публичный материал.
3. Проверь Voice & call to action. Voice влияет на стиль, а факты берутся из выбранных notes. CTA копируется в результат; поставь реальный конечный URL. Проверь Media note после каждой смены продукта из-за #68.
4. Выбери формат и стиль. Для первых практических попыток удобен Clear, Auto tags выключены. Это редакторский выбор для этих сценариев, а не измеренный победитель настроек.
5. Подтверди I confirm the selected changes belong in this announcement и нажми Write the announcement.
6. Прочитай результат рядом с Source notes. Перепроверь каждое число, условие, «now», «released», автоматическое действие и обещание. Отдельно проверь отсутствие сведений только из voice sample.
7. Исправь обычный текст через Edit draft, X — прямо в карточках. Повторная генерация всегда отдельное действие. Ошибка оставляет прежний draft; причина и исходный ответ видны в Generation records.
8. Скачай Markdown и, если нужен разбор происхождения, JSON record. До исправления #66 для обычных форматов отдельно сохрани исходный pack или список commit/file references.
9. Перенеси текст в редактор площадки, выполни preview и опубликуй вручную. Для X проверка в настоящем composer обязательна: локальный счётчик приблизительный.
10. После публикации сохрани публичный URL, дату, конечный текст и исходный range/pack рядом с локальными файлами. Экспорт и preview сами по себе ещё не публикация.

Не используй Copy whole thread как готовый один пост: он добавляет номера и соединяет несколько карточек. В X переноси каждую карточку через Copy this post. Media notes прикреплёнными изображениями не являются.

## Сценарий 1 DevLog по последним коммитам PatchPitch

**Задача:** рассказать разработчикам, как теперь можно исследовать неудачную генерацию и сохранить её исходный ответ. Конечный результат — вручную опубликованный DevLog на DEV. Это update о состоянии main; отдельный tag/Release из него не следует.

### Получить проверяемые факты

Git import пока отсутствует, поэтому первый шаг выполняется вручную. В корне PatchPitch:

```powershell
git log --no-merges --oneline -10
git log --no-merges --oneline f5baf58..6f84004
git diff --stat f5baf58 6f84004
git diff f5baf58 6f84004 -- patchpitch
```

Этот фиксированный range включает сохранение generation attempts и исправление связи single-card record с последующими правками. Сверь `patchpitch/static/generation-records.js`, `patchpitch/generator.py` и `patchpitch/static/social-editor.js`. Для нового будущего DevLog замени base/head на свой проверенный диапазон; не копируй приведённые факты автоматически в следующий выпуск.

### Заполнить продукт

| Поле | Значение для этого прохода |
| --- | --- |
| Product name | PatchPitch |
| What does it do? | A local writing studio that turns reviewed change notes into editable announcements. |
| Who is this for? | Indie developers trying the current main branch |
| Release | Development update after PR 64 |
| Format / Style | Devlog / Clear |
| CTA | https://github.com/drevendev/PatchPitch |

В What changed? вставь четыре строки:

```text
Current main retains each generation attempt in the browser tab, including successful drafts and rejected model responses.
The author can inspect the original response and rejection reason. A failed attempt leaves the existing draft and manual edits intact; retry requires a new explicit action.
Copy record JSON and Download record JSON export the input snapshot, original API response, error and model settings. Manual edits are a separate snapshot and are not automatically revalidated.
Single-card rewrite records can export later edits to that card while it still belongs to that attempt. A subsequent rewrite does not attach its current card to the superseded attempt. Records disappear on refresh or closing the tab; downloading a record does not provide a session restore feature.
```

В Voice можно указать: `Calm direct prose. Concrete behavior and limitations. No invented measurements.` Подтверди все четыре заметки и сгенерируй один draft. Именно такой вход в новом live прогоне дал принятый Devlog.

### Довести текст

1. Сверь четыре темы с кодом и Source notes. Последняя должна объяснять границу record export и восстановления сессии.
2. Проверь, что текст не обещает autosave, persistent history, восстановление после refresh или автоматическое исправление model output.
3. Через Edit draft сделай заголовок понятным читателю. Например: `Inspect failed generations without losing your draft`. Это пример редакторского заголовка, не фактическое обещание сохранения после закрытия.
4. Добавь короткий собственный контекст проблемы, только если можешь подтвердить его. Для примера ошибочного ответа можно использовать уже публичный безопасный материал, а не чужие приватные notes.
5. Сохрани Markdown. Отдельно запиши `f5baf58..6f84004` и ссылки на проверенные файлы: provenance обычного Devlog пока теряется в record (#66).

### Ручная публикация в DEV

Открой [новый пост DEV](https://dev.to/new), перенеси заголовок в Title, а из Markdown body убери дублирующий `#` заголовок. Прочитай Preview: абзацы, список изменений, ссылка и ограничения должны отображаться ожидаемо. Добавь подходящие tags в поля DEV; Auto tags PatchPitch не равны метаданным площадки. Нажми Publish после своей редакторской проверки. DEV поддерживает Markdown и отдельные поля rich + markdown; детали описаны в [официальном Editor Guide](https://dev.to/p/editor_guide).

После публикации открой публичный URL и проверь, что там окончательный текст. Сохрани URL рядом с Markdown и range. Сценарий завершён, когда читатель может открыть опубликованный DevLog и понять, что изменилось в main и где его попробовать.

## Сценарий 2 Пост или тред о существующем PatchPitch в X

**Задача:** показать другим indie developers существующий локальный workflow. Конечный результат — один вручную опубликованный пост или связный тред; без объявления неподтверждённого нового Release.

### Подготовить вход

1. В Reviewed fact packs выбери `PatchPitch · public workflow`, нажми Load facts.
2. Прочитай sources. Для одиночного поста оставь C01, C02, C03, C04. Для треда добавь C05 о записанном демо. C06/C07 — отдельные инженерные истории, они не нужны этому краткому знакомству. C09 planned оставь выключенным.
3. Сохрани Product/release загруженного pack. При необходимости менять контекст проверь его заново: #46 пока не сбрасывает подтверждение при каждой существенной правке.
4. CTA — репозиторий PatchPitch. Media note можно очистить или указать реальный screenshot редактора. Затем такой screenshot нужно будет прикрепить самостоятельно.
5. Для треда выбери X Thread, 5 posts, Writing goal `Show a real result`, Style Clear. Для короткого знакомства — X Single с тем же goal.

### Проверить и отредактировать

У треда полезен такой порядок: что делает продукт → как выбираются факты → как сверяются источники → как редактировать и экспортировать → где посмотреть/попробовать. Это редакторский план; модель не обязана выдать точную структуру без правок.

Проверь, что hosted demo назван recorded и не обещает live inference посетителю. Source IDs не должны описываться как доказательство истинности. Не добавляй claims о пользователях, времени экономии или увеличении охвата: таких фактов во входе нет.

Правь текст в карточках. При перестановке следи за CTA: редактор сохраняет слова и не переносит её автоматически на новую последнюю карточку. Regenerate this post заменяет только выбранную карточку; из-за #47 после rewrite заново прочитай исходные notes, а не ориентируйся только на старые warnings.

Для X Single возможна такая ручная финальная редакция:

```text
PatchPitch turns selected release notes into editable announcements using Gemma through local Ollama. Inspect the source notes, edit the draft, and copy it when you're ready. Human review is still essential.

https://github.com/drevendev/PatchPitch
```

Этот текст составлен как редакторский пример по публичным фактам; это не новый необработанный model response. Проверь его в composer перед использованием.

### Ручная публикация в X

Скачай Markdown и JSON record до перехода на другую вкладку. Открой composer X в своём аккаунте и вставь одну карточку через Copy this post. ## Сценарий 3 Объяснение Crafting Batch для игроков Idle Fantasy Shop

**Задача:** подготовить понятный feature guide для игроков и вручную опубликовать его в devlog игры на itch.io. Встроенный pack описывает исторический patch 0.12. Перед публикацией проверь эти условия в актуальной игре; из наличия pack не следует, что 0.12 — свежий релиз сегодня.

### Подготовить вход

1. Выбери `Idle Fantasy Shop · 0.12 patch`, нажми Load facts.
2. Оставь выбранными C01 Crafting Batch и C08 сохранение/backup. Остальные изменения и internal C09 не нужны короткому объяснению механики.
3. Открой оригинальный C01. Основные условия: Workshop 10 → до 3 entries; Workshop 50 → до 5; 1–99 завершённых cycles на entry; это не количество готовых предметов; entries выполняются последовательно один раз; нехватка ингредиентов блокирует очередь; workers могут поставлять материалы, сама Batch их не собирает.
4. Проверь C08: backup из Settings нужен перед сменой устройства или очисткой browser data. Не превращай это в утверждение о новой опасности обновления.
5. Format Community post, Style Clear, Auto tags off. CTA — ссылка на игру из pack. Очисти Media note от предыдущего проекта.
6. Сгенерируй и отредактируй. Язык этого draft — English; русскую версию подготовь вручную отдельно.

### Убрать двусмысленность и ложную новизну

В новом live ответе opening «can now manage multiple jobs at once» требует правки. Замени его на прямое описание продукта и очереди. Пример ручной финальной редакции:

```text
In Idle Fantasy Shop, the Batch Board lets you plan an ordered crafting list. Workshop level 10 unlocks up to 3 job entries; level 50 expands it to 5. Each entry requests 1–99 completed crafting cycles, not that many finished items. Duplicate entries are allowed.

The list runs once, in order, then stops. Missing ingredients hold up the current entry; later entries cannot skip ahead. Workers can supply materials, but the Batch does not gather them.

Export a backup from Settings before changing devices or clearing browser data.

https://drevengames.itch.io/idle-fantasy-shop
```

Текст основан на pack, но перед использованием его должен принять владелец игры. Для evergreen guide удали слова «new», «now», «just shipped» и не объявляй текущую дату датой выпуска 0.12. Если игра уже изменила условия, сначала обнови исходные notes и проверь их заново.

### Ручная публикация на itch.io

Скачай текст и record, отдельно сохрани исходный pack/provenance из-за #66. В dashboard itch.io открой собственный проект Idle Fantasy Shop и создание devlog post. Перенеси заголовок вроде `How the Crafting Batch works`, затем абзацы в редактор. Обычная вставка Markdown в rich text editor может требовать ручного форматирования — проверь preview.

Прикрепи реальный screenshot Batch Board с нужным уровнем/entries; Media note сама файл не загрузит. Для такого текста выбери тип публикации, соответствующий инструкции о механике, а не объявлению нового релиза. Проверь имя игры, условия, язык и рабочую ссылку, затем опубликуй вручную. Devlogs связаны со страницей проекта и поддерживают изображения/вложения, как описано в [официальном описании itch.io](https://itch.io/updates/introducing-devlogs).

Открой публичный devlog и проверь, что игрок видит последовательную очередь, а не обещание параллельного крафта. Сохрани URL и финальный текст. Это законченный сценарий для существующей функции; новый билд игры для публикации такого guide не требуется, если описание соответствует текущему поведению.

## Как оценить пользу первых трёх проходов

Для каждого случая запиши исходный pack/range, формат, время подготовки фактов, время правок, какие смысловые ошибки пришлось убрать, final Markdown и URL публикации. Если выполнялся только preview, поле URL публикации оставь пустым.

После трёх случаев ответь на практические вопросы: получилось ли быстрее получить текст, который хочется публиковать; какие правки повторяются; терялся ли контекст; можно ли вернуться на следующий день; что пришлось делать вне продукта. Не сравнивай эти результаты с выдуманным временем ручного написания и не называй один собственный эксперимент внешним спросом.

### Этап 1 Надёжно закончить текущую сессию

**Пользовательский результат:** подготовить текст для одного продукта, проверить его, сохранить работу и вернуться завтра.

### Этап 2 DevLog из последних коммитов

**Главный следующий функциональный сценарий, P1 [#8](https://github.com/drevendev/PatchPitch/issues/8).** Пользователь выбирает репозиторий и диапазон, получает проверяемые кандидаты фактов, утверждает нужное и выходит с DevLog.

| Шаг | Что должен делать продукт |
| --- | --- |
| Выбор | Локальный repo + последние N коммитов, явные base/head или сохранённый вручную published_head |
| Фиксация | Показать точные SHA, branch и рабочее дерево; незакоммиченные изменения исключить по умолчанию |
| Извлечение | Читать bounded metadata/diff, учитывать reverts/merges, фильтр пути, generated/binary/oversized files |
| Review | Кандидаты фактов с commit/file/ref; сохранённые условия; Include/Exclude до генерации текста |

| Редактура | Существующий Devlog editor, source snapshot, JSON record; можно подготовить X summary из тех же утверждённых фактов |
| Завершение | Save/Open, экспорт и ручная публикация; published_head меняется только по явному действию после реальной публикации |

Первый реальный acceptance case — PatchPitch `f5baf58..6f84004` и текст про generation records. Второй — выбранный игровой repo с настоящими изменениями. Для MVP достаточно local Git и минимального различения committed/verified/released из #48. Весь портфельный Fact Pack v2, GitHub OAuth, облачная модель и автопубликация не нужны для первого законченного прохода.
