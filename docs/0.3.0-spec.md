# PatchPitch 0.3.0 — автоматическая подготовка публикаций

Текущий статус на 24 октября 2026: **0.3.0 выпущен**. [Итоги выпуска](release-closeout-0.3.0-2026-10-24.md) содержат финальный коммит, проверки и артефакты; оставшиеся задачи — в [бэклоге](backlog.md). Формулировки о будущем релизе ниже сохраняют контекст исходной спецификации.

Спецификация следующего релиза, 22 октября 2026 года. Номер 0.3.0 — рабочий до формирования release candidate. Документ задаёт требования к будущей реализации. Исходная точка: `main`, HEAD `44ca597`, с локальными изменениями Quillgrain/Telegram; наличие этих изменений не означает выпуск релиза.

Реализация начата в `0.3.0.dev0`: доступные команды, примеры и ограничения описаны в [headless workflow](headless.md). Этот документ сохраняет требования полного релиза; наличие команды само по себе не закрывает живые и редакционные критерии приёмки.

## 1. Результат релиза

Разработчик задаёт продукт, источники изменений, аудиторию и авторский профиль. Один запуск PatchPitch без браузера готовит согласованный пакет для **Telegram, Twitter/X, DEV и GitHub**. Пакет сохраняется на диск, допускает редактуру и повторное использование. Интерфейс становится одним из способов работы с тем же конвейером.

Фиксируем четыре площадки из запроса. Они определяют ближайший roadmap; новые социальные сети не входят в этот релиз.

Обязательные решения:

- **X: ровно шесть релевантных хэштегов в каждом готовом посте.** Для треда правило применяется к каждой карточке. Количество шесть — продуктовая политика владельца; рекомендации «до трёх» не используются для X.
- **Автоматический запуск без UI — P0.** CLI работает без браузера, Playwright, HTTP-сервера и интерактивных подтверждений. Его можно вызвать из планировщика, CI, shell или другого инструмента.
- **Quillgrain внутри рабочего процесса.** Поддерживаются готовый bundle и сборка выбранного локального профиля средствами установленного engine.
- **Статья о релизе на DEV — приёмочный сценарий.** PatchPitch готовит статью о собственном обновлении и умеет передать её в DEV как черновик.

## 3. Состав релиза

**P0, обязательный состав:**

1. Устанавливаемый CLI, JSON/TOML job, план запуска, постоянные артефакты и возобновление.
2. Генерация для всех четырёх площадок; EN/RU с отдельным выбором языка и голоса для каждого результата.
3. X hashtag policy: шесть тегов, каталог с доказательствами выбора, резервирование длины, проверка после редактуры.
4. Quillgrain: импорт и сборка выбранного pack через установленный engine, проверка контракта, неизменяемые snapshots.
5. DEV article: Markdown/метаданные и адаптер создания/обновления удалённого черновика.
6. Совместимость с текущими сессиями и импорт CLI-результатов в редактор.
7. Настоящий запуск на изменениях PatchPitch и подготовка статьи об этом релизе через приложение.

**P1, после P0, без задержки основного релиза:** создание draft release в GitHub, отправка готового текста ботом в Telegram, импорт собственной аналитики X для обновления каталога тегов.

Прямая отправка постов в X, встроенный постоянно работающий планировщик, новые площадки, облачная модель, автоматическая генерация видео и обучение голоса по обратной связи остаются за пределами 0.3.0. Автоматическое расписание обеспечивает внешний планировщик, вызывающий CLI. Для генерации и экспорта аккаунты площадок не нужны.

## 4. Контракт работы без UI

### 4.1. Команды

Ниже — интерфейс спецификации. Реализованные команды и порядок настройки приведены в [headless workflow](headless.md).

```text
python -m patchpitch run --job campaign.toml --out artifacts/campaigns/patchpitch-0.3.0 --json
python -m patchpitch run --job campaign.toml --out artifacts/campaigns/patchpitch-0.3.0 --plan --json
python -m patchpitch resume --run artifacts/campaigns/patchpitch-0.3.0 --json
python -m patchpitch validate --run artifacts/campaigns/patchpitch-0.3.0 --json
python -m patchpitch export --run artifacts/campaigns/patchpitch-0.3.0 --kind session --out artifacts/campaigns/patchpitch-0.3.0/session.json
python -m patchpitch voice build --config voice.toml --out artifacts/voice/telegram-ru
python -m patchpitch deliver --run artifacts/campaigns/patchpitch-0.3.0 --channel dev --mode draft --json
```

После установки доступен эквивалентный entry point `patchpitch`. Запуск из чистой установки документируется для Windows и Linux. UI и browser dependencies не требуются для CLI; готовый Ollama с установленной моделью необходим для inference.

`run` сам последовательно выполняет настроенные этапы. Параметр `--plan` проверяет конфигурацию, локальные источники, ссылки на файлы, зависимости и оценку количества запросов; не вызывает модель и не пишет на площадки. Для модельного Git extraction точный набор фактов и последующая пригодность тегов становятся известны только после соответствующего этапа.

Каждая команда завершается сама. stdin не используется для вопросов; по умолчанию его можно закрыть. Сетевые вызовы и inference имеют таймауты. Неоднозначная конфигурация возвращает машинную ошибку, которую можно исправить в job. Отсутствующий пакет, модель или токен не вызывает установку, скачивание или открытие браузера.

### 4.2. Job и выбор источников

Поддержать JSON и TOML, без выполнения кода из задания. Все относительные пути разрешаются от файла job. JSON Schema версионируется как `patchpitch.job/v1`; неизвестные поля, дублирующиеся ключи и несовместимая версия отклоняются.

Пример формы задания для будущей версии. Указанные файлы создаются пользователем; пример не утверждает наличие подготовленных фактов, голосов или сильных тегов.

```toml
schema_version = "patchpitch.job/v1"
campaign_id = "patchpitch-0.3.0"
product_profile = "product-profile.json"
writing_goal = "development"

[source]
kind = "reviewed_fact_pack"
path = "reviewed-facts.json"

[execution]
max_model_requests = 6
inference_attempts_per_step = 1
continue_other_targets_on_error = true

[voices.telegram_ru]
provider = "quillgrain"
mode = "bundle"
path = "voices/telegram-ru/voice-bundle.json"

[voices.longform_en]
provider = "quillgrain"
mode = "bundle"
path = "voices/longform-en/voice-bundle.json"

[[targets]]
id = "telegram-ru"
channel = "telegram"
format = "telegram"
language = "ru"
voice = "telegram_ru"

[[targets]]
id = "x-en"
channel = "x"
format = "x_thread"
post_count = 5
language = "en"
style = "clear"
hashtag_catalog = "x-hashtags.json"
hashtag_policy = "x-six-v1"

[[targets]]
id = "dev-en"
channel = "dev"
format = "dev_article"
language = "en"
voice = "longform_en"

[[targets]]
id = "github-en"
channel = "github"
format = "github_release_notes"
language = "en"
style = "clear"
```

Источники поддерживают два режима:

- `reviewed_fact_pack`: явно выбранные факты и их provenance. Job фиксирует, какие факты разрешено использовать; дополнительных кликов перед каждой генерацией нет.
- `git_range`: repository, base/head, явный список файлов или разрешённых путей, лимиты extraction и политика `candidate_selection`. Режим `all_valid_candidates` разрешает автоматически собрать ограниченный набор прошедших структурные проверки кандидатов. Режим `selection_file` применяет сохранённый выбор по устойчивым ID и digest. Несовпадение selection с источником требует нового файла выбора, без обхода через `confirmed=true`.

Автоматически выбранные модельные кандидаты сохраняются со статусом `machine_selected_unreviewed`; job не превращает их в человечески проверенные факты. Они пригодны для автоматической подготовки черновика. В результатах сохраняются этот статус и исходные diff. При превышении 15 фактов/6000 символов конвейер возвращает `FACT_BUDGET_EXCEEDED`, сохраняя кандидатов; молчаливого отсечения нет.

Git-режим сохраняет текущие ограничения по диапазону, файлам и размерам diff. Dirty tree раскрывается и исключается. По умолчанию Git даёт `writing_goal=development`; заявление о выпущенном релизе требует отдельного источника, подтверждающего выпуск. Отсутствие новых коммитов — успешный `no_changes` без вызова модели и повторного использования старого анонса.

### 4.3. Состояние, ошибки и повторный запуск

Конвейер: `input → facts → voice → target plan → generation → validation → export`. Для Git extraction каждый batch имеет собственный checkpoint. Для каждого target хранится отдельный статус: `pending`, `running`, `succeeded`, `failed` или `blocked`. Редакционный статус (`unreviewed`/`reviewed`) хранится отдельно от технического успеха.

В каталоге запуска обязательны:

- `manifest.json`: версия приложения и схемы, resolved job, статусы и ссылки на файлы.
- `sources.json`: фиксированные факты, provenance, range/SHA и результат отбора.
- `attempts/`: вход и доступный исходный ответ каждой попытки, ошибки, настроенная и реально возвращённая модель, request hash, настройки и время.
- `outputs/<target-id>/`: исходный результат, отдельно текущая редактура, экспорт и validation report.
- `voices/`: точный использованный bundle/lock либо явное отсутствие авторского профиля.

Запись checkpoints атомарная. После прерывания сохраняются законченные этапы и факт незавершённого запроса. `resume` продолжает незаконченные шаги, не генерирует заново успешные targets и не перетирает правки. Повтор inference после неудачи допускается явной командой возобновления; скрытых повторов и автоматического исправления текста нет.

Идентичность шага включает digest источников, job, голоса, промпта/адаптера, каталога тегов и настройки модели. Изменение входа создаёт новую ревизию, не переписывая историю. Повтор `run` с тем же job и out возвращает существующий завершённый результат без inference; существующий каталог с другой идентичностью возвращает `RUN_INPUT_MISMATCH`. Параллельная запись в один run блокируется. Работа разных runs с моделью ограничивается общим локальным lock; занятый engine возвращает ошибку без бесконечного ожидания.

Если один target не проходит проверку, остальные можно завершить согласно job. Итоговый статус — `partial_failure`, код выхода ненулевой; успешные файлы остаются доступны. Общая ошибка источников блокирует все зависимые targets.

| Exit code | Значение |
| --- | --- |
| 0 | Успех, переиспользованный результат или `no_changes` |
| 2 | Ошибка job, входных файлов или версии схемы |
| 3 | Недоступна необходимая зависимость/модель, не прошла проверка voice либо занят engine |
| 4 | Ошибка inference, extraction или проверки результата, включая частичный сбой |
| 5 | Ошибка внешнего адаптера или неизвестный исход удалённого запроса |

С `--json` stdout содержит один JSON-объект с `schema_version`, `run_id`, `status`, `targets`, `artifacts`, `errors`, `warnings`. Прогресс идёт в stderr. Токены и полные voice samples не попадают в логи. Код выхода и JSON согласованы; исключения не превращаются в успешный запуск.

## 5. Twitter/X: шесть тегов с основанием для выбора

### 5.1. Правило результата

Для `x_single` и каждой карточки `x_thread` финальный текст содержит **ровно шесть уникальных хэштегов**, сравниваемых после Unicode normalization и без учёта регистра. Это обязательная проверка готовности к экспорту для X, включая ручные правки. Повторение подходящего тега в разных карточках допускается; внутри одного поста дубли запрещены.

Теги хранятся структурированно и добавляются приложением. Модель пишет основной текст, опираясь на уже выбранные теги и остаточный бюджет; случайная генерация тегов свободным текстом не используется. Политика других площадок независима: шесть относится именно к X. Для DEV tags — метаданные статьи.

Резервировать длину шести тегов, разделителей и точного CTA **до** генерации текста. Проверять окончательный текст целиком. Нельзя удалять теги, условия использования функции или обрезать последнее предложение ради лимита. При невозможности вместить пост — `X_LENGTH_EXCEEDED` с сохранённой попыткой. Для треда CTA по умолчанию остаётся только в последней карточке.

Стандартный профиль 0.3.0 использует предел 280 weighted characters; X описывает веса Unicode, emoji и URL и рекомендует `twitter-text` для подсчёта. Проверка должна быть общей для CLI/UI и сверенной с официальными conformance fixtures; до этого текущий `x-estimate-v1` продолжает явно называться оценкой. [Документация X о подсчёте длины](https://docs.x.com/fundamentals/counting-characters).

### 5.2. Что значит «имеют силу»

Выбор должен сочетать соответствие теме, нужную аудиторию и наблюдаемую активность. Простое наличие слова в diff и популярность широкого тега сами по себе недостаточны.

В P0 используется локальный версионированный каталог `patchpitch.hashtag-catalog/v1`. Для каждого кандидата нужны:

- `tag`, язык/рынок, темы и целевая аудитория; список нежелательных контекстов.
- Основание релевантности: факты/темы кампании, к которым подходит тег.
- `evidence`: тип (`own_analytics` или `public_sample`), источник/URL либо ссылка на локальный импорт, дата наблюдения, временное окно и размер выборки.
- Доступные показатели: например, число релевантных постов/авторов в выборке, отклики или переходы собственных публикаций. Неизвестные величины остаются `null`.
- Редакторская оценка соответствия аудитории, дата пересмотра и срок актуальности свидетельств. Первоначальная политика — 30 дней, задаётся явно и записывается в результат.

Каталог можно подготовить вручную по наблюдаемым данным или импортировать из разрешённого источника. Личная пометка «хороший тег» сохраняется как редакторская оценка, но не заменяет `evidence`. Тег проекта может участвовать на тех же условиях; брендовый тег не добавляется автоматически ради заполнения шести мест.

Порядок отбора:

1. Отсечь неверный язык, неподходящую аудиторию/смысл и просроченные или отсутствующие свидетельства активности.
2. Для каждой карточки сопоставить кандидатов с её фактическим содержанием, а не только с продуктом в целом. В треде после reorder/rewrite проверять соответствие заново.
3. Ранжировать оставшихся по явной, версионированной политике: тематическое соответствие, соответствие аудитории, качество/свежесть наблюдений, затем наблюдаемый результат в сопоставимых данных. Популярность широкого тега не отменяет первые фильтры.
4. Выбрать шесть с разумным сочетанием общих, тематических и нишевых тегов, без жёсткой квоты на тип. При равенстве использовать стабильный порядок; случайного выбора нет.
5. Сохранить `hashtag_decisions.json`: все выбранные теги, причины, fact IDs, evidence refs, дату каталога, отклонённых кандидатов и версию политики. Любые числовые баллы — оценка политики, а не прогноз охвата.

План треда с темами и source IDs строится до выбора тегов; исходную extraction/outline попытку также сохраняем. Готовый текст повторно проверяется на соответствие плану. Если на карточку нет шести подходящих тегов с актуальными свидетельствами, target останавливается с `HASHTAGS_INSUFFICIENT_EVIDENCE`. Остальные площадки продолжают работу. Публикационный текст не дополняется выдуманными «трендовыми» тегами.

Офлайн-запуск использует зафиксированный каталог и даты наблюдений; сетевой поиск во время генерации не обязателен. В комплект примеров входит небольшой каталог с проверяемыми публичными наблюдениями и сроком актуальности. Отдельный будущий импорт собственной аналитики улучшает ранжирование. Наблюдаемая активность не доказывает причинный прирост охвата: приложение показывает основание выбора и оставляет неизвестное неизвестным.

## 6. Форматы площадок

| Канал | Обязательный результат | Проверка и особенности |
| --- | --- | --- |
| Telegram | Связный пост, plaintext/Markdown export, источник фактов и выбранный голос | Разговорный авторский текст; общий бюджет текста, CTA и тегов. Отдельный формат от короткой рекламы |
| X | Single или 3–7 карточек, plain text каждой, общий Markdown | Ровно шесть тегов на карточку, единый счётчик, source IDs и media notes отдельно |
| DEV | `article.md` и `article.json`: title, description, body_markdown, tags, optional canonical_url/main_image/series | Полноценная статья: проблема, решение, воспроизводимый пример, ограничения и вывод автора, если подтверждён фактически |
| GitHub | `release-notes.md` и JSON с repository, version/tag, base/head и source map | Изменения по смыслу, breaking changes/миграции только из источников; ссылки на commits/PR при наличии |

Для Telegram текущий экспорт сохраняет переносы и Markdown markers. Публикационный адаптер должен отдельно реализовать escaping/entities: вставка Markdown не гарантирует форматирование. Bot API задаёт для обычного `sendMessage` 1–4096 символов после разбора entities. До внедрения адаптера приложение сохраняет собственную консервативную проверку длины. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

DEV article строится из тех же разрешённых фактов, но имеет собственную структуру и бриф. Длинная статья не получается механическим растягиванием X-поста. Если запрошены конкретные результаты тестов, замеры или «до/после», а источников нет, это пробел редакционного брифа: соответствующий раздел не выдумывается. Кодовые примеры берутся из проверенного материала или явно помечаются как предлагаемый интерфейс.

GitHub release notes отделены от статуса размещения релиза. По одному Git diff можно подготовить черновик заметок о разработке; формулировки «выпущено» требуют подтверждения выпуска. Генерация заметок сама не создаёт tag, Release или запись о публикации.

## 7. Quillgrain внутри PatchPitch

### 7.1. Два режима подключения

1. **Bundle:** CLI/UI принимает существующий `quillgrain.voice-bundle/v1` и проверяет его engine verifier.
2. **Local pack:** пользователь задаёт путь к pack и bindings/overlays в конфигурации voice. PatchPitch вызывает библиотечный compiler установленного Quillgrain, создаёт bundle и сохраняет его snapshot. Ручной предварительный экспорт через другое приложение больше не обязателен.

Engine остаётся отдельной optional dependency с проверенным диапазоном совместимости или зафиксированной ревизией для локальной установки. Необходимы обычная инструкция установки и диагностическая ошибка при отсутствии engine. Текущий `pip install -e PATH` остаётся путём разработки; выпуск не предполагает доступность `quillgrain` на PyPI без проверки.

Исходный контракт уже существует в соседнем проекте: `compile_context(...)`, `consumer.bundle(...)`, `loads_bundle(...)`, `verify_bundle(...)`. На дату спецификации локальный engine обозначен `0.1.0rc3`. Реализация использует его API и контракт, не копирует engine в PatchPitch и не вводит отдельную несовместимую схему голоса. См. текущую [инструкцию интеграции](quillgrain-voice.md); соответствие версии проверяется при подготовке релиза.

### 7.2. Параметры и сохранность контекста

Voice config включает pack path, bindings, overlays, language, register, tags, example_pool, max_chars и ожидаемый build при необходимости фиксации. Для consumer: target `patchpitch`, host `ollama`. Register берётся из явно выбранного профиля, а не жёстко назначается любому тексту как `maker_announcement`.

Telegram и X используют `social.telegram` и `social.x`. Для DEV/GitHub P0 использует существующий `social.longform` вместе с явно указанным register. Разделение на новые channel tags требует совместимого изменения пакетов Quillgrain, а не заявления, что engine уже их поддерживает.

Обязательные свойства:

- Проверять bundle schema, build/lock identity, разрешения host/retrieval, language/register/channel и бюджет; возвращать устойчивый код Quillgrain внутри ошибки CLI.
- Сохранять приоритеты и scope правил, authorship/role примеров, отчёт об omissions и выбранном pool. Пустой pool не заменять общими примерами скрыто.
- Применять голос отдельно от фактов и формата. Примеры не дают права перенести авторский опыт, шутку, продуктовые обещания или планы в новый текст.
- Авторский профиль заменяет общий preset. Явное сочетание конфликтующих настроек в job отклоняется; другой preset не подмешивается молча.
- Несовместимый язык/канал, повреждённый lock и превышенный budget блокируют только зависимые targets. Fallback к generic voice допускается только как заранее указанная отдельная конфигурация с явной записью в результате.
- Переключение профиля действует на будущие запросы. Rewrite старой карточки и восстановление сессии используют её исходный snapshot.
- Private/local-only материалы доступны только локальной модели и приватному run/session. В DEV payload, публичный source map, CI artifacts и telemetry уходят только специально подготовленные публичные данные.

Текущий guard против длинных дословных заимствований сохраняется. Проверка структуры/хэшей не доказывает стилевое сходство; приёмка голоса проводится на реальных новых фактах. Каждый target хранит build IDs пакетов, engine/adapter versions и hash фактической сборки промпта.

## 8. DEV: черновик через сам PatchPitch

P0 включает явную команду `deliver --channel dev --mode draft`. Генерация локального пакета доступна без credentials; для передачи используется переменная окружения `PATCHPITCH_DEV_API_KEY`. Значение не сохраняется в job/session, логах и run manifest.

Адаптер передаёт title, body_markdown и метаданные через Forem API с явным `published=false`. Создание статьи и обновление по ID поддержаны API; используются `POST /api/articles` и `PUT /api/articles/{id}`. [Контракт Forem API](https://developers.forem.com/api/v1#tag/articles/operation/createArticle).

Перед передачей проверяются текущие отредактированные файлы и их digest, а также список разрешённых публичных полей. Voice bundle, оригинальные ответы модели, пути частного checkout и внутренние заметки не добавляются в body. Экспорт в DEV не запускает повторную генерацию.

Удалённая квитанция содержит `article_id`, URL при наличии, timestamp, отправленный content hash и статус `remote_draft`. После успешного создания повторный вызов с тем же контентом использует квитанцию; с изменённым контентом обновляет тот же принадлежащий пользователю черновик. Если статья уже опубликована, команда draft не меняет её статус и возвращает `REMOTE_ALREADY_PUBLISHED`.

У API и локального checkpoint нет общей транзакции. Потеря ответа после POST даёт `delivery_unknown`; команда не повторяет POST автоматически. Для сверки предусмотреть `--existing-id <id>` с проверкой владельца/контента и привязкой найденного draft к run. Удалённый draft и публикация различаются в статусах и baseline.

Для GitHub P1 используется отдельный адаптер draft Release. API допускает `draft=true`, а создание Release может затрагивать tag, поэтому существование и соответствие tag проверяются отдельно. Это не побочный эффект генерации Markdown. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#create-a-release).

Публичная публикация является отдельной будущей операцией с явным выбором готового артефакта и площадки. Она не требует UI по архитектуре. Запись baseline меняется после подтверждённой публикации, отдельно для каждой площадки; подготовка, export и remote draft её не сдвигают.

## 9. Изменения архитектуры и совместимость

- Добавить `__main__.py`, CLI entry point и packaging с явным включением prompts/static/fact packs. Базовая установка поддерживает CLI; browser-тесты и Quillgrain оформляются отдельными зависимостями.
- Вынести orchestration в небольшой общий Python-слой, вызывающий существующие `generator`, `social`, Git extraction и валидацию. CLI не управляет браузером и не отправляет HTTP-запросы самому себе. FastAPI/UI использует те же операции и ограничения.
- Добавить версионированные job/run/hashtag schemas и файловый store. Session JSON редактора не переиспользовать как скрытый исполняемый job.
- Общие форматирование, подсчёт X, выбор тегов и проверки текущих правок обслуживают и CLI, и UI. Проверка перед export/deliver относится к текущему тексту, не только к исходному model response.
- Ввести платформенные поля DEV/GitHub и явное сопоставление Quillgrain register/channel. Не привязывать новую архитектуру ко всем форматам через `format.startswith("x_")`.
- Сохранять открытие старых session/profile файлов. Если нужны новые поля, определить версию/миграцию. Старая X-карточка без шести тегов открывается без изменения текста с отметкой legacy; её исходный экспорт остаётся доступен как legacy, а готовность по новой X policy требует явного обновления и проверки.
- Импорт run в редактор сохраняет факты, точный голос, оригинальные попытки и текущую редактуру. Повторное открытие не делает inference и не меняет данные CLI run без явного сохранения.

Каталоги запусков по умолчанию размещаются под игнорируемым `artifacts/campaigns/`. Для CI публикуется только выбранный sanitised export; весь run с частным голосом не становится downloadable artifact по умолчанию. В релиз входят пример вызова из Windows Task Scheduler и пример GitHub Actions для self-hosted runner с готовым локальным Ollama. Hosted runner без модели не объявляется рабочим inference-сценарием.

## 10. План реализации

| Этап | Результат, который можно проверить | Зависимость |
| --- | --- | --- |
| A | Packaging, job schema, shared runner, запуск готовых фактов без UI | Основа |
| B | Постоянные attempts/checkpoints, resume, машинный Git-режим, session export | A |

Каждый этап оформляется отдельным проверяемым изменением. Дату релиза определяет выполнение P0 и приёмка, а не наличие документа или слияние промежуточного PR.

## 11. Критерии приёмки

| ID | Сценарий | Условие готовности |
| --- | --- | --- |
| H01 | Чистый CLI-запуск Windows/Linux, stdin закрыт, браузера и web-сервера нет | Один job создаёт четыре результата и JSON summary; процесс завершён |
| H02 | Внешний планировщик вызывает тот же job | Нет вопросов/кликов; источник, модель и параметры фиксируются; повторный run не дублирует inference |
| H03 | Ollama отсутствует, модель не установлена или запрос истёк | Ненулевой exit, структурная ошибка и сохранённая попытка без fallback |
| H04 | Прерывание между Git batches/targets и resume | Завершённые этапы/правки сохранены; история исходных ответов неизменна |
| H05 | Git unattended и сохранённый выбор | Нет обязательного UI; machine-selected не обозначены как human-reviewed; stale selection блокируется |
| X01 | Single и Thread EN/RU | В каждом итоговом посте ровно шесть уникальных тегов, для каждого есть актуальное основание |

| Q01 | Bundle и сборка локального pack | Одинаковый выбранный контекст доступен CLI/UI; engine/build/lock и сборка записаны |
| Q02 | Нет engine, неверный язык/register/channel, hash/budget error | Явная диагностика; существующие тексты и snapshots сохранены |
| Q03 | Смена voice после генерации и rewrite старой карточки | Rewrite использует оригинальный voice; новый профиль относится к новым запросам |
| P01 | Экспорт четырёх площадок | Общая фактическая основа; статьи, заметки релиза и короткие посты сохраняют условия и статус изменений |
| D01 | Создание DEV draft и последующее обновление | Сохраняется article ID; repeat не создаёт дубликат; текущие правки дошли без новой генерации |

| S01 | Старые sessions и импорт CLI run | Точные тексты, карточки, voice и records восстановлены без inference |

| R01 | Реальная модель на изменениях PatchPitch | Сохранены вход, raw outputs, ошибки, ручная редактура и отдельная оценка смысла/голоса |

Автоматические проверки покрывают критические ветки orchestration, неизменяемость истории, общий счётчик/теги, scope Quillgrain и отсутствие дубликатов доставки. Для внешних API используются contract tests и отдельный добровольный live draft check. MOCK-тесты не объявляются проверкой качества текста. Итоговые CLI-примеры выполняются из установленного пакета вне корня репозитория, а не только через исходники.

## 12. Статья о релизе через PatchPitch

Рабочий угол статьи: **«From commits to a launch kit: making PatchPitch run without a browser»**. Финальное название выбирается по готовому тексту. Основная версия — английская для DEV, отдельно русский пост для Telegram и X-анонс с шестью обоснованными тегами на карточку.

Материал собирается после реализации:

1. Зафиксировать точный range и подтверждённое состояние релиза; подготовить факты о реально работающих возможностях.
2. Включить новый CLI на этих источниках: Git → факты → Quillgrain при выбранном профиле → DEV article, Telegram, X, GitHub notes.
3. Сохранить первоначальный ответ, неудачи и редактуру. Проверить команды на чистой установке; добавить только реальные замеры и проверки с указанием условий.
4. Построить статью вокруг прежнего ручного процесса, нового примера job/команды, осмысленного выбора тегов, роли авторского профиля и оставшихся ограничений. Объяснить, какие части были сгенерированы и что автор отредактировал.
5. Передать утверждённую редакцию командой DEV draft, открыть получившийся черновик и проверить Markdown, код, ссылки и метаданные. Готовый материал не называет ещё не выпущенные возможности доступным релизом.
6. После фактического выпуска и авторской редакции опубликовать статью отдельным действием; её реальную ссылку использовать в остальных площадках. До появления ссылки CTA остаётся явным незаполненным полем, а не выдуманным URL.

Релиз считается подготовленным после выполнения P0 и проверки пакета, включая DEV draft. Публичная статья, GitHub Release и анонсы имеют собственные фактические статусы; в документации выпуска отмечаются только действительно выполненные действия.
