# PatchPitch 0.4.0 — редакторский конвейер статьи

Статус: **спецификация для обсуждения, реализация не начата**. Дата: 24 октября 2026 года. Проверенная исходная точка: `main`, [`92791bf`](https://github.com/drevendev/PatchPitch/commit/92791bfcb5e3c94c2bc2888d5864aae559ebb37b). Номер 0.4.0 обозначает следующий функциональный релиз; версия пакета, теги и опубликованный 0.3.0 этим документом не меняются.

## 1. Пользовательский результат

Я выбираю проверенные факты и авторский профиль, получаю план истории, редактирую его и пишу статью через Quillgrain. Затем могу переписать один раздел, сохранив остальную работу, расставить реальные скриншоты, GIF и видео, посмотреть статью целиком и сохранить её в DEV черновиком. Три анонса X связаны с этой статьёй и получают финальную ссылку после моей ручной публикации в DEV.

Критерий пользы — уменьшение ручной работы между проверенными фактами и материалом, который автор готов публиковать. Валидный JSON или отсутствие предупреждений сами по себе не означают хорошую статью.

CLI и UI используют один документ, правила ревизий и проверки. Все этапы доступны без браузера и интерактивного stdin; UI предоставляет удобное редактирование и просмотр. Генерация, принятие правок, экспорт и передача в DEV — отдельные операции.

Важные границы текущей реализации:

- Sections в ответе модели — ещё не редактируемый план статьи. В них нет постоянной identity и операций адресного изменения.
- `current_result` читает правленый Markdown и проверяет метаданные; `validate_run` не перестраивает смысловую карту абзацев после произвольных правок. Исторические source maps нельзя показывать как проверку нового текста.
- Цели существующего campaign job генерируются из общих фактов независимо. X сейчас не объявляет зависимость от принятого DEV-текста и его будущего публичного URL.
- В DEV payload пока нет `main_image`, реестра медиа и защиты от перезаписи чужой ручной правки того же собственного черновика. Ownership и защита от повторного POST уже есть и сохраняются.
- Успешный прошлый редакционный цикл включал ручную работу автора и агента. Это не доказательство наличия соответствующих команд в продукте.

## 3. Объём релиза

Обязательный P0:

1. Редакторская рабочая папка и общий документ с планом, содержимым, медиа, ревизиями и зависимостями.
2. Редактируемый план: идея, читательский результат, последовательность разделов и привязка фактов.
3. Написание разделов через Quillgrain; ручная правка и перегенерация выбранного раздела с сохранением остальных.
4. Полное локальное превью со скриншотами, GIF и видео; экспорт Markdown и медиа-манифеста.
5. Создание/обновление одного DEV-черновика из конкретной принятой ревизии, включая публичные изображения и cover.
6. Три самостоятельных анонса X из этой ревизии: разные углы, ровно шесть обоснованных тегов с обязательным `#DEVCommunity`, привязка финального URL.
7. Восстановление после ошибки/закрытия, совместимость старых runs/sessions, UI/CLI-паритет и живой приёмочный сценарий.

В будущий 0.4.0 также переходят уже готовые в `main`, но ещё не выпущенные исправления [подсчёта X-ссылок](x-length.md) и CSP-safe browser waits. Они переиспользуются и регрессионно проверяются, а не реализуются повторно.

Не входят в P0: публикация статьи или постов, новый планировщик, Short.io/аналитика переходов, сбор популярности тегов, автогенерация/запись/монтаж медиа, новый видеохостинг, дополнительные провайдеры модели и обещание поддержки 4B. Существующие Telegram/GitHub workflows сохраняются; новые адаптеры для них не нужны этому сценарию.

Задача «видео со звуком и управлением **внутри DEV**» остаётся отдельным отложенным [пунктом бэклога](backlog.md#dev-video-with-sound-and-controls). 0.4.0 обязан честно показывать доступный fallback, но не обязан решать эту задачу или создавать YouTube-аккаунт.

## 4. Один документ и его состояния

### 4.1. Вход

Новая конфигурация `patchpitch.editorial-job/v1` задаёт:

- campaign ID, продукт, аудиторию, writing goal, язык EN/RU, авторский ракурс и CTA;
- источник: существующий reviewed fact pack **либо** конкретный target существующего campaign run, из которого копируются подготовленные источники и provenance;
- Quillgrain bundle/local pack с явными language/register/channel, либо явно выбранный обычный preset;
- бюджет модельных запросов, каталог X, требование `#DEVCommunity` и три разных угла анонсов;
- необязательный media manifest с локальными файлами и публичными соответствиями.

При импорте campaign run можно отдельно выбрать перенос его текущей статьи. Без этого переносится только источник: план можно построить до первого редакторского текста. Исходный run открывается только для чтения, исходные responses и правки в нём не меняются. Для Git переиспользуется уже существующий extraction/review workflow; новый отдельный Git importer в этот релиз не добавляется.

`machine_selected_unreviewed` сохраняется как статус источников. Его нельзя повысить до `reviewed` фактом успешной генерации. Автор может подготовить план и кандидатов текста, но должен отдельно принять факты перед готовностью статьи к доставке.

### 4.2. Структура рабочей папки

Предлагаемый контракт, ещё не реализован:

```text
editorial-work/
  manifest.json                 # schema, текущая ревизия, состояния и зависимости
  inputs/                       # неизменяемые источники, конфигурация, provenance
  voices/                       # приватные bundles и build identities
  revisions/<revision-id>.json  # принятые версии документа
  attempts/<attempt-id>.json    # запрос/ответ/ошибка/кандидат, включая отвергнутые
  media/<content-hash>.<ext>    # импортированные локальные байты
  receipts/                    # отдельные DEV delivery и публикационные записи
  exports/<revision-id>/       # производные Markdown/HTML/manifest/X тексты
```

Документ `patchpitch.editorial-document/v1` включает `document_id`, `revision_id`, `parent_revision_id`, identity источников, approved plan, metadata, ordered sections, asset placements, review records и X dependencies. Каждый раздел имеет постоянный `section_id`, каждый блок — `block_id`; перестановка не меняет ID. Удалённый ID не назначается новому разделу. Текст хранится без автоматического форматирования/перефразирования при сохранении.

Блоки P0: paragraph, list, code reference, media reference. Code reference указывает на конкретный сохранённый snippet/hash, а не поручает модели воспроизвести команду. Metadata содержит title, description, до четырёх уникальных DEV tags, cover asset и явный AI disclosure. В тело DEV не дублируется H1 из title.

Начальные текстовые пределы: до 12 разделов, до 96 блоков суммарно, до 3000 символов в paragraph и до 32000 символов в собранном body, включая код и media markup. Title — до 120, description — до 300 символов. Вход использует существующий бюджет до 15 фактов/6000 символов; его расширение не является скрытой частью релиза. Превышение возвращает именованную ошибку до записи/запроса модели; усечение или потеря блока недопустимы.

### 4.3. Состояния и зависимости

Состояния выводятся из принятых данных: `sources_ready` → `outline_ready` → `draft_ready` → `review_ready`. Независимо показываются `media_ready_for_dev`, `dev_sync_state`, `x_state` и состояние финальной ссылки. Успешная модель не переводит текст в `review_ready`.

Превью, валидация, DEV receipt и X-серия ссылаются на `revision_id` и hash экспортного содержимого. После принятой правки старые результаты сохраняются как исторические, а зависящие результаты получают `stale`. После перестановки раздела тоже обновляется ревизия. Изменение только финального URL не переписывает принятую статью и не запускает модель.

`review_ready` требует принятия текущего плана/текста автором, покрытых обязательных фактов, отсутствия блокирующих ошибок и актуальности review к этой ревизии. Редактирование источников, голоса, title/body/cover или AI disclosure аннулирует соответствующее подтверждение; локальная пометка в журнале не меняет публичные данные.

## 5. План и Quillgrain

План содержит один тезис, аудиторию, обещанный читателю результат, предложенный title, ракурс и ordered sections. У раздела есть цель, разрешённые source IDs, обязательные условия/ограничения, желаемые code/media refs и ориентир длины. Каждый включённый факт должен попасть в раздел либо получить явное решение автора об исключении с причиной. Исключение не редактирует исходный fact pack.

По умолчанию для личного блога используется **первое лицо единственного числа**. Язык, ракурс и голос — явные поля. «Мы» допустимо только после выбора командного ракурса. Промпт не изобретает опыт, воспоминания, эмоции или историю неудачи: для них нужны исходные авторские заметки. Мнение/переход можно пометить как editorial context, но такой блок не становится доказательством факта.

Полезная структура DEV: начать с конкретной проблемы и результата, рано показать работающий пример или результат, объяснить решения через наблюдения, закончить применимым выводом. Это рекомендации редакторского шаблона. Список обязательных секций «введение/установка/ограничения» не должен превращать каждую статью в README. Не требовать выдуманного эксперимента или лишних дисклеймеров ради шаблона.

Автор может добавить/удалить/переставить раздел, изменить цель и источники, закрепить раздел от модельной перезаписи, принять план. Изменение плана после написания делает затронутые разделы требующими review; остальные тексты сохраняются.

Quillgrain остаётся существующим локальным адаптером. Каждая попытка фиксирует bundle/build/pack identity, engine version, language/register/channel и эффективную сборку промпта. Внешний изменившийся pack не подхватывается автоматически. Операция выбора нового build явная: существующие тексты сохраняются, новая попытка использует новый snapshot. Неподдерживаемый engine или неправильная область bundle дают ошибку до inference; тихого fallback к generic preset нет.

Приватные правила и примеры голоса не экспортируются в HTML, Markdown или DEV payload. Стилевые примеры никогда не разрешают новые продуктовые заявления. Проверка на совпадения с примерами — сигнал для редактора, не гарантия уникальности или узнаваемого голоса.

## 6. Написание и адресная редактура

Для P0 написание идёт последовательно по разделам: одна модельная попытка на раздел, без скрытых повторов. План — отдельная попытка. Перед запуском CLI/UI показывают верхнюю оценку запросов, учитывая планирование X; превышение общего бюджета блокирует запуск до inference. Завершённые разделы переиспользуются при resume.

Запрос выбранного раздела получает approved plan, разрешённые ему факты, указанные источники кода, сохранённый voice snapshot и ограниченный read-only контекст соседних разделов. Контекст соседей нужен для связности, но не является новым источником фактов и не расширяет область записи. Размер контекста ограничен; пропуски раскрываются, незаметного усечения источников нет.

Операции: ручная правка, «сделать конкретнее/короче», свободная инструкция автора, переписать только выбранный раздел. Сначала появляется кандидат и diff. Принятие и отклонение — отдельные операции. Модель не может менять title, metadata, plan, другие sections, code/media bytes или placements через ответ section rewrite.

Гарантии записи:

- Каждая мутация указывает `expected_revision_id` и уникальный operation ID. Устаревший ответ сохраняется в attempts, но не заменяет более новую ручную правку.
- Принятие создаёт новую неизменяемую ревизию и атомарно переключает manifest под блокировкой. Неизменённые разделы и их IDs/текст/code/media refs сохраняются побайтно; служебная identity всего документа меняется.
- Ошибка inference, невалидный ответ, отмена или закрытие UI сохраняют принятую версию. Неудачный кандидат и исходный ответ доступны для разбора.
- Повтор operation ID не создаёт вторую правку и второй inference. После uncertain inference автоматический новый запрос не выполняется: сначала восстановление сохранённого ответа, затем явное решение о новой попытке.
- Откат возвращает выбранное содержание новой ревизией, сохраняя последующие/отвергнутые попытки в истории. «Закреплённый» раздел требует явного снятия защиты перед модельной заменой.

Source map относится к конкретным блокам конкретной ревизии. После ручной правки фактологического блока его review сбрасывается; UI не утверждает, что старые ссылки подтверждают новую формулировку. Блок с неизвестным source ID или кодом, отсутствующим в выбранном snippet, не проходит автоматическую проверку. Семантику, опыт автора и истинность цитирования принимает человек; схема этого не доказывает.

Свободный Markdown поддерживается как явный импорт с показом преобразования в блоки и diff. Если структура/источники не восстанавливаются однозначно, импорт сохраняется кандидатом с `needs_review`; он не перезаписывает разделы и не получает автоматически старую карту источников. Прямое изменение производного `exports/article.md` не редактирует документ: изменение обнаруживается hash-проверкой, а пользователь получает путь явного импорта.

## 7. Медиа и полное превью

### 7.1. Настоящие файлы и размещение

Asset имеет `asset_id`, вид (`image`, `gif`, `video`), content hash, тип/размер, локальный относительный путь, alt/caption, provenance и необязательный `public_url`. Placement указывает стабильный block/section ID и порядок. Cover задаётся отдельно; замена cover не удаляет inline placement того же файла.

P0 принимает PNG/JPEG/WebP, GIF, MP4 и необязательные poster/WebVTT. Импорт копирует байты в рабочую папку без изменения исходника; никакой генерации, конвертации или транскодирования. Стартовые локальные пределы: 30 assets, 20 MiB на изображение/GIF, 200 MiB на видео, 500 MiB суммарно; они проверяются до чтения всего файла. Это лимиты PatchPitch, не утверждение о лимитах DEV.

Проверяются MIME/signature, разрешённое расширение, размеры, дубликаты, существование и hash. SVG/HTML/исполняемые вложения в P0 не поддерживаются. Неизвестная длительность/аудиодорожка помечается unknown, а не подменяется выдуманным значением. Alt обязателен для содержательных изображений; автор может явно отметить декоративное.

Локальный путь остаётся внутри рабочей папки после resolve, включая symlink/junction-проверку. Preview server отдаёт только собранный preview bundle, не произвольные файлы по пути из URL. Перемещение/резервное копирование папки сохраняет медиа. Для передачи всей редакторской работы используется folder bundle; прежний session JSON не выдаётся за перенос файлов.

### 7.2. Два режима просмотра

«Локальный» показывает актуальную статью с настоящим Markdown-форматированием, метаданными, heading anchors, кодом, cover, inline images/GIF и desktop/mobile шириной. Видео имеет видимые controls, не запускается автоматически, позволяет включить звук, перемотать и выбрать доступные субтитры. Звук проверяется на ролике с реальной аудиодорожкой; GIF не называется видео со звуком.

«DEV export» показывает собранный вариант с публичными URL и явными карточками неподдерживаемых embeds. Это приближение к DEV, а не исполнение Forem. Рядом доступны экспортный Markdown, список unresolved media и последняя проверенная удалённая draft revision.

Рендерер — общий для CLI/UI, с ограниченным Markdown и escaping/sanitization. Raw script/iframe/event handlers, `javascript:`/`file:` и произвольное выполнение Liquid не допускаются. Для поддерживаемого Liquid embed в локальном режиме используется безопасная placeholder-карточка. CSP не ослабляется ради рендерера, нет `unsafe-eval` и обхода CSP в тестах.

HTML preview и проверка файлов не делают inference и не обращаются к DEV. По умолчанию используются локальные assets и не загружаются внешние ресурсы; публичная картинка без локальной копии отображается placeholder до явного сетевого просмотра. Preview bundle не содержит источников, voice bundles, API key, raw responses или абсолютных приватных путей. Для просмотра достаточно статического bundle и необязательного локального сервера на loopback; базовый CLI не требует FastAPI/Playwright.

### 7.3. Медиа в DEV

Доступный P0-путь: автор задаёт уже размещённый HTTPS URL для каждого экспортируемого asset. PatchPitch собирает обычные Markdown images, передаёт cover через `main_image` и предоставляет manifest соответствий hash → URL. Создание хостинга, GitHub Pages deployment и загрузка файлов в DEV через недокументированный endpoint не подразумеваются.

Для видео поддерживается явный fallback: poster/CTA на существующий плеер, например уже используемый GitHub Pages. В DEV export он подписан как переход к видео. Локальный `<video controls>` не превращается в raw HTML video для DEV. Будущий разрешённый embed провайдера требует отдельной проверки в настоящем DEV-черновике; поддержка локального MP4 не закрывает отложенную задачу встроенного DEV-видео.

Если локальное обязательное медиа не имеет публичного соответствия, draft delivery блокируется с перечислением asset IDs. Автор может явно исключить placement и принять новую ревизию. Нельзя молча отправить `localhost`, `file:`, локальный путь или broken placeholder. HTTPS URL не доказывает доступность: сетевой preflight явный, ограниченный по редиректам/размеру и исключает private/loopback назначения; результат имеет время проверки. Недоступность не запускает поиск нового хостинга.

## 8. DEV-черновик

Принятую ревизию сначала валидируют и экспортируют без сети. Доставка выполняется отдельной явной командой или кнопкой. На экране/в плане видны revision, title, payload hash, account/target ID при наличии и статус каждой media-ссылки. Секрет берётся из `PATCHPITCH_DEV_API_KEY`, как сейчас; локальная подготовка без ключа работает.

Расширяется существующий adapter с allowlist полей: title, description, body_markdown без повторного H1, DEV tags, разрешённый cover `main_image`, AI disclosure и **`published=false`**. Не отправлять editorial document или session целиком. YAML front matter в импортированном body разбирается как отдельный вход: конфликтующие publication/metadata поля отклоняются или переводятся в metadata через явное принятие. Перед отправкой в body front matter не остаётся; оно не может переопределить draft-only payload.

Receipt хранит article ID, безопасную preview/edit ссылку, submitted payload/hash, локальную revision и наблюдаемое удалённое состояние. Приватная preview-ссылка не становится финальным URL X и не попадает в публичный export.

Повтор без изменений не создаёт новый draft. Для PUT сначала проверяются ownership, отсутствие публикации и удалённая версия против последнего подтверждённого receipt. Если автор успел изменить draft в DEV, вернуть `REMOTE_DRAFT_CHANGED` и показать конфликт; автоматической перезаписи нет. Разрешение конфликта — отдельный импорт remote revision или явное обновление после просмотра diff. Если API не возвращает достаточное содержимое для сравнения, состояние unknown блокирует слепой PUT.

Существующее восстановление `delivery_unknown` и omitted AI disclosure сохраняется: сравнивается исходный отправленный payload, повторный blind POST запрещён, reconciliation обновляет тот же принадлежащий автору draft. Потерянный ответ не превращается в повод создать копию. Изменение body/cover/disclosure требует нового payload hash.

Автоматически не объявлять remote preview проверенным только по HTTP 2xx. Окончательная media-приёмка — просмотр сохранённого draft в DEV: картинки, cover, GIF, fallback видео, заголовок и метаданные. Приложение сохраняет отдельно статус доставки и отметку автора о просмотренной ревизии. Публикация через продукт в 0.4.0 не добавляется.

## 9. Три анонса X и финальная ссылка

Анонсы строятся из принятой статьи и разрешённых ей исходных фактов, а не из всего сырого Git-диффа. Каждая серия хранит source article revision/hash. Три варианта по умолчанию: результат для пользователя, конкретный опыт/эксперимент из статьи, практический пример. Если исходники не содержат эксперимента, автор выбирает другой угол; модель его не изобретает.

Каждый вариант — самостоятельный X Single. Существующие threads остаются доступными в старом workflow; создавать новую логику тредов для этой задачи не нужно. Перегенерация одного варианта сохраняет правки и медиа остальных, используя уже существующий social generation/validation как основу.

Правила:

- Ровно шесть тегов в каждом готовом анонсе; `#DEVCommunity` обязателен. Остальные пять выводятся из темы и свежего каталога. Обязательный тег также должен присутствовать в выбранном каталоге с подходящим evidence; нехватка данных даёт объяснимый blocker, а не случайную замену.
- Сохраняется topical validation и observation ledger. Публичная выборка означает обоснованную релевантность, не доказанный охват. Сила тегов не подменяется сгенерированным score популярности.
- До появления финальной ссылки используется типизированный слот `article_public_url`; в бюджете ему заранее отводятся 23 символа плюс разделители. Текстовый маркер не считается URL. Статус такого анонса — `awaiting_public_url`, copy-ready экспорт блокируется; редакторское превью доступно.
- После ручной публикации автор задаёт финальный DEV URL и, если известен, article ID. При явной сетевой проверке API должен подтвердить public article и identity; без неё ссылка остаётся `unverified`, её можно хранить, но не помечать verified/copy-ready. Draft preview URL с `?preview=...` запрещён для этого слота.
- Подстановка подтверждённой ссылки детерминированна и не вызывает модель. Обновляется только управляемый CTA-слот, не произвольные похожие URL в авторском тексте. После изменения CTA заново проверяются шесть тегов и весь 280-символьный бюджет через `x-estimate-v2`.
- Меняется статья — X-варианты получают `stale`. Автор либо явно принимает прежнюю формулировку как подходящую новой ревизии, либо перегенерирует выбранные. Старые варианты и ручные правки сохраняются.

Экспорт даёт три отдельных TXT, общий Markdown и manifest с углом, ссылкой, тегами/evidence и длиной. Отправки в X нет. В живой приёмке 0.4.0 можно использовать уже опубликованную статью для проверки финального URL: публиковать новый материал ради теста не требуется.

## 10. CLI и UI

Ниже — **предлагаемые новые команды**, не существующая инструкция запуска. Старый `patchpitch run --plan` остаётся dry run кампании; генерация редакторского плана называется `outline`, чтобы не смешивать эти действия.

```text
patchpitch editorial init --config editorial.toml --out WORK --json
patchpitch editorial outline --work WORK --json
patchpitch editorial accept --work WORK --candidate ATTEMPT --expected-revision REV --json
patchpitch editorial draft --work WORK --json
patchpitch editorial revise --work WORK --section S03 --instruction-file edit.txt --json
patchpitch editorial apply --work WORK --patch edits.json --expected-revision REV --json
patchpitch editorial preview --work WORK --out PREVIEW --json
patchpitch editorial validate --work WORK --json
patchpitch editorial export --work WORK --out EXPORT --json
patchpitch editorial deliver --work WORK --channel dev --mode draft --json
patchpitch editorial x --work WORK --json
patchpitch editorial bind-url --work WORK --url DEV_PUBLIC_URL --verify --json
```

`outline`, `draft`, `revise` и `x` создают попытки/кандидаты; `accept`/`apply` меняют принятую ревизию. Для `draft` сохраняются кандидаты каждого раздела, включая завершённые до ошибки. `apply` принимает строго типизированные операции для плана, metadata, ручных блоков, review и asset mappings; все используют expected revision/operation ID. У каждого мутирующего вызова есть operation ID в запросе/ответе; повтор идентичен.

Для headless batch явно доступна политика `accept_valid_candidates=true`. Она принимает структурно проверенные кандидаты в рабочий draft, но не выдаёт human review и не разрешает доставку сама по себе. `init`, `apply`, `preview`, `validate`, `export`, принятие кандидата и подстановка URL не вызывают модель. Любая сетевая проверка URL и DEV delivery объявлена отдельно. Все inference-действия поддерживают dry-run оценку через общий флаг `--dry-run`; скрытых retries нет.

Exit codes сохраняют нынешнюю семантику: 2 input/schema/revision conflict, 3 dependency/busy, 4 inference/validation/stale readiness, 5 delivery, 130 interruption. stdout содержит один JSON summary, stderr — прогресс без секретов. Ошибки имеют code, entity ID и понятное действие: например, `REVISION_CONFLICT`, `SECTION_LOCKED`, `MEDIA_UNRESOLVED`, `ARTICLE_NOT_REVIEWED`, `REMOTE_DRAFT_CHANGED`, `ARTICLE_URL_UNVERIFIED`, `ANNOUNCEMENTS_STALE`.

UI показывает последовательность «Источники → План → Текст → Превью → DEV draft → X», текущую revision и статусы зависимостей. Можно вернуться на предыдущий этап. У раздела доступны ручной редактор, источники, фиксация, запрос правки и diff кандидата. Не требуется заново генерировать всё, чтобы сменить подпись изображения. Кнопки доставки/экспорта объясняют конкретные blockers. Закрытие вкладки не теряет принятую работу; незавершённая правка имеет локальный recovery buffer, который не становится принятой ревизией без действия автора.

## 11. Архитектура и совместимость

Новый editorial domain слой отвечает за документ, зависимости и операции. CLI и локальный API вызывают его напрямую. Prompt assembly остаётся рядом с longform/social/voice, а рендерер и DEV adapter потребляют принятые exports. Не помещать редакторские операции в DOM-only код и не импортировать UI-сервер из CLI.

`patchpitch.job/v1`, `patchpitch.run/v1` и `patchpitch_session` v1 остаются читаемыми без переписывания старых original/snapshot. Импорт создаёт новый editorial workspace, сохраняет identity исходника и отдельно маркирует восстановленные вручную границы разделов. Нельзя автоматически разделить неизвестный Markdown и объявить все source maps проверенными. Новая форма экспортируется своим versioned bundle, а существующий session export остаётся представлением текста/карточек с объявленными ограничениями.

Runtime/source fingerprint, engine/model identity и policy versions сохраняются у попыток. Возобновление незавершённого inference требует совместимого runtime; новый fingerprint не обходится миграцией старого snapshot. Чтение, просмотр и экспорт принятого документа без inference доступны после обновления при поддерживаемой document schema. Миграция явная, с копией и отчётом, без преобразования исходных доказательств.

Baseline quality: 12B/600-second конфигурация из [Linux-прогона 0.3.0](linux-live-2026-10-24.md), а не обещание одинакового качества у любой модели. У 0.4.0 больше запросов; время измеряется заново, старые timings не переносятся как benchmark. При отсутствии engine/model обычное открытие документа и preview работают; выбранная генерация объясняет недостающую зависимость.

## 12. Приёмка

### Автоматические проверки

| Группа | Что должно быть доказано |
| --- | --- |
| Plan/document | Стабильные IDs, перестановка/удаление, явные omissions, несовместимые источники, malformed schema и expected revision conflicts |
| Section rewrite | Успех, ошибка, отмена, stale response и crash recovery; изменение только выбранного раздела, остальных текстов/code/media hashes — ноль |
| Voice | Snapshot на попытку, EN/RU/register/channel, новый build только явно, отсутствие engine, неподдерживаемая версия, защита от переноса voice examples в факты |
| Review/dependencies | Правки сбрасывают актуальные review/delivery/X states; schema validation не выдаётся за смысловую проверку; исторические maps остаются историческими |
| Media/preview | Реальные image/GIF/video fixtures, звук/controls/subtitles, перенос папки, hashes, alt, отсутствующий файл/URL, размеры, path traversal/symlink, XSS и работа при строгой CSP |
| DEV | Draft-only, cover и disclosure, отсутствие H1/front matter override, повтор без дубля, uncertain POST/PUT, remote edits conflict, чужой/опубликованный article, omitted disclosure и сохранность нового локального текста |
| X | Три различных назначения, обязательный `#DEVCommunity` среди шести evidence-backed tags, stale evidence, URL slot/23, несколько URL, 280/281, замена только CTA, stale article и preview URL rejection |
| Compatibility/package | Старые sessions/runs открываются без изменения originals; новый CLI работает из чистого wheel без FastAPI/Playwright; source archive содержит схемы и fixtures |
| UI/CLI parity | Одинаковые mutations и hashes, full preview текущих ручных правок, Save/Open, запрет stale apply, редактура одного раздела сохраняет остальные |

Основной suite проверяет обычный режим без optional engine; отдельный pinned Quillgrain CI проверяет интеграцию с нулём skipped cases. Linux package job собирает wheel/sdist, проверяет collection из исходного архива и чистую установку. Браузерные ожидания используют locator assertions под настоящей CSP. Любой упавший первый CI остаётся фактом; зелёный rerun не считается доказательством устранения flaky test.

### Живой сценарий и редакторская польза

Провести по будущей отдельной авторизации два прохода: статья о PatchPitch из проверенных фактов и материал о другом реальном проекте. Для каждого сохранить исходники, модель/digest/runtime, voice identity, операции, необработанные ответы, принятые правки, запросы и timings.

Минимальная проверка конвейера:

1. Принять факты, получить и отредактировать план; написать статью с Quillgrain.
2. Внести ручную правку в один раздел, закрепить другой, переписать третий. Проверить побайтную сохранность незатронутых разделов и отсутствие лишнего inference при retry/resume.
3. Разместить скриншот, GIF и MP4 с настоящей аудиодорожкой, poster и субтитрами. Проверить локальное воспроизведение и полный mobile/desktop preview текущей revision.
4. Привязать заранее подготовленные публичные assets; получить DEV draft. Проверить его фактический вид, выполнить одну правку через приложение и обновить тот же draft; затем воспроизвести remote edit conflict.
5. Получить три X-анонса. Проверить placeholder blocker, затем подставить URL уже опубликованной статьи: без нового inference, с шестью тегами и корректным бюджетом. Ничего не публиковать.
6. Закрыть/открыть рабочую папку, проверить историю и состояние, экспортировать публикационные файлы без приватных voice/source данных.

Измерять: количество inference-запросов, время до первого preview/готового draft, активное время правок автора, сколько разделов пришлось переписать вне PatchPitch, количество ручных переносов текста/ссылок/медиа между инструментами. Сравнивать с зафиксированным повтором текущего workflow на сопоставимых исходниках, не с выдуманной оценкой времени.

Продуктовая приёмка: оба материала можно довести до готового draft внутри конвейера без обязательного внешнего переписывания всей статьи; адресная правка не требует переноса других разделов; final URL подставляется без ручного редактирования трёх файлов. Автор принимает связность, первое лицо, конкретность примеров и достоверность фактов. Если один результат остаётся README вместо статьи и требует полной внешней переделки, автоматические тесты не закрывают этот gate.

## 13. Порядок реализации после принятия спеки

1. **Документ и операции:** schema, import источников, immutable revisions, locks/CAS, review/dependency graph. Критерий: редактирование/сохранение/восстановление без модели и без потери старых форматов.
2. **План и разделы:** общий CLI/API, Quillgrain, кандидаты/diff/accept, адресная редактура. Критерий: одна правка не меняет другие разделы; история и request budget проверены.
3. **Медиа и preview:** asset registry, block placements, renderer, переносимые exports. Критерий: полный актуальный preview и честное различие local/DEV.
4. **DEV draft:** публичные mappings, cover, payload, receipt и remote conflict. Критерий: обновление одного реального draft без дублей и потери правок.
5. **X и end-to-end:** три угла, зависимость от статьи, URL binding, шесть тегов; package/CI/live/editorial acceptance. Критерий: два законченных кейса и измерения пользы.

Версия dev/rc, tag, GitHub Release и любые публикации — последующие отдельные действия. Этот документ их не запускает. Полный legacy suite и приёмочные проверки выполняются при реализации; для подготовки спеки проверена только указанная группа из 100 существующих тестов.

## 14. Внешние контракты и открытые решения

Сверено 24 октября 2026 года:

- [Forem API overview](https://developers.forem.com/api): сохраняется v1 `Accept` contract. [Параметры создания/обновления статьи](https://developers.forem.com/api/v0) документируют `main_image` и приоритет front matter; это основание для явной сборки cover и запрета body override.
- [DEV Editor Guide](https://dev.to/p/editor_guide/) описывает Markdown images/GIF, отдельный title, cover URL, до четырёх tags и поддерживаемые embeds. Документация не подтверждает inline MP4 с произвольного GitHub Pages URL; для него принят внешний player fallback.
- Внешние контракты могут отличаться от документации: перед реализацией remote adapter и перед приёмкой повторно проверить их на тестовом draft. Секретные preview URL не сохранять в публичных доказательствах.

Рабочие решения этой спеки: отдельный editorial namespace/workspace, folder bundle для медиа, последовательная генерация разделов, публичные media mappings без нового upload-сервиса, DEV draft-only, три X Single и ручная публикация вне приложения. Их изменение требует обновления документа, а не молчаливого расширения реализации. Выбор библиотеки Markdown/sanitizer остаётся техническим решением этапа 3 после проверки лицензии, обслуживания и CSP; требования безопасности и headless-пакета от выбора библиотеки не зависят.
